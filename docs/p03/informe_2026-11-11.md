**Fecha:** 11 de noviembre de 2026, America/Mexico_City.  
**Rama local:** `verificacion/p03-work`.  
**Base SDK:** `65c75c8ba1f79c9af91d8634b1edd03bf25f1747`.  
**Core realmente probado:** `e23a134b199687399f28840c73bfe7b8073cf444`.  
**Estado:** cambios sin commit, listos para revision; sin publicacion ni fusion.

## Cambio

Antes, tipo/rango aceptaban retorno 1, diagnostico esperado y encabezado, aunque
stderr incluyera un informe de memoria. Ahora ambos delegan en un helper que
inspecciona stdout y stderr antes de validar el error del lenguaje. Los informes
ASan/UBSan/LSan fallan explicitamente. Los errores fatales de LSan se registran
como infraestructura bloqueada; nunca como aprobacion.

Se mantienen los nombres CTest y marcadores de exito anteriores. Se anaden
logs opcionales completos y una bateria independiente del verificador. No se
modifico el CMake raiz del SDK, codigo de produccion C, datos de las pruebas,
Core ni Lab.

La automatizacion nueva comprueba solo tipo/rango contra builds suministrados,
registra procedencia y configuracion, exige coherencia de rutas e instrumentacion
y verifica que las entradas no cambien durante la ejecucion. No sustituye los
dos originales P0.3 que no se localizaron en la auditoria anterior.

## Validacion personal

Entorno: Debian 13 x86_64, GCC 14.2.0-19, CMake/CTest 3.31.10, Python 3.12.14.
SDK compilado en Debug y con ASan/UBSan contra bibliotecas Core ya existentes.
No se compilo ni modifico Core durante esta etapa. Raylib 5.5 precompilada se
utilizo para configurar/compilar el SDK; no se ejecuto una ventana real.

| Comprobacion | Resultado |
|---|---|
| Configurar y compilar SDK Debug y ASan/UBSan | Correcto |
| Bateria P0.3 independiente | **65/65**: 56 verificadores y 9 controles de clasificacion LSan |
| Suite SDK Debug completa | **32/32**, incluidos tipo/rango con los wrappers reforzados |
| Automatizador, tipo/rango Debug | `PASS_FUNCTIONAL`; ambos programas retornan 1 y ambos verificadores 0 |
| Automatizador, perfil instrumentado | `BLOCKED_INFRASTRUCTURE`, retorno global 2 |
| Tipo/rango instrumentados | Ambos registran error fatal LSan por `ptrace`, retorno del programa 86 y del wrapper 1 |
| Control LSan independiente limpio y con fuga intencional | Ambos bloqueados por la misma restriccion |
| `LSAN_OPTIONS=exitcode=0` suministrado al CLI | `INVALID_CONFIG`, retorno 3; no se ejecuto VM ni control LSan |
| Builds Debug enviados como perfil instrumentado | `INVALID_CONFIG`, retorno 3 antes de ejecutar la VM |
| Directorio de informe existente | Rechazado con 3; informe previo conservado byte por byte |
| Fuentes, cabeceras, bibliotecas y caches durante las dos comprobaciones directas | Sin cambios |

Los 65 casos son pruebas del verificador y de clasificacion; no prueban ausencia
de fugas en el lenguaje. No se ejecutaron las 32 pruebas SDK bajo ASan en esta
etapa ni se ratificaron resultados locales de P0.2.

## P0.3 → P0.2

Los verificadores reforzados estan listos en una rama local SDK independiente.
Rechazan contaminacion ASan/UBSan/LSan incluso con retorno y diagnostico esperados.
Se validaron 65/65 casos del verificador y 32/32 SDK Debug. Core permanece intacto.

En este entorno, los casos directos tipo/rango y el control LSan estan bloqueados
por `ptrace`; no se atribuye ese resultado al Core corregido de P0.2. Los
9/9, 30/30 y 32/32 comunicados por P0.2 se mantienen como evidencia de ese equipo.

Siguiente comprobacion compartida: ejecutar `scripts/p03/verificar_errores.py`
contra los builds A/B identificados, en el equipo donde LSan funciona, y compartir
`report.json`, `report.md`, streams de tipo/rango y controles. Para cerrar esos
dos casos se necesita `PASS_SANITIZERS`, control limpio valido, control con fuga
detectada y ausencia de informes de sanitizadores en los casos reales. No fusionar
ramas automaticamente.
